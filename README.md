# SundiroSPUnlock

把「新大洲本田」蓝牙**无感解锁**独立成 **SpringBoard 插件**，不再依赖官方 App。
车况遥测 / 小组件 / 深链控制仍由官方 App 侧组件负责，两者互不干扰。

**当前版本：1.3.5** ｜ 支持 `iphoneos-arm64e`（RootHide）与 `iphoneos-arm64`（rootless）

> **设计目标**：通过越狱实现比官方 App 更强的蓝牙解锁 —— **拿着手机靠近车辆，按车辆解锁键秒解锁**。

---

## 为什么能独立

解锁协议**完全自包含**，取自官方 App 的实测数据：

| 依赖项 | 来源 |
|:--|:--|
| 4 帧协议报文 | 离线造帧（XOR 校验 + `AA AA` 尾） |
| 49 组 `(R, R3)` 配对 | 硬编码常量表（官方 App 实测采集） |
| 32 字节常量 | 硬编码 |
| 服务/特征 UUID | `FFF0 / FFF1 / FFF6`（硬编码） |
| 网络 / token / 官方 App | **完全不需要** |

**核心机制**：iOS 会无限期保持一个「挂起的蓝牙连接」（pending connect）。
插件在 SpringBoard 里挂上它，车一进入范围 iOS 就自动完成连接，插件立刻发四帧解锁。

> 官方 App 也能做这件事，但**会被 iOS 挂起**。**SpringBoard 永远不会被挂起** —— 这就是独立成插件的意义。
> 实测：pending connect 存活 **6 小时 26 分**，期间零人工干预，车一出现即连上并解锁。

### v1.2.2 修复「关一次蓝牙后再也不连车」（2026-10-10 22:44 · **协议零改动**）

| 项目 | 内容 |
|:--|:--|
| **现象** | 关一次蓝牙（或蓝牙抖动）后，插件**再也不连车**，解锁彻底失效，直到重启用户空间 |
| **根本破绽** | `_connecting` 守卫只在 `didConnect` / `didFailToConnect` / `didDisconnect` 三处清零，而 `centralManagerDidUpdateState` 的 PoweredOff 分支**什么都不做**；系统取消 pending connect 时**不保证回调** ⇒ 守卫永久停在 YES，`tryConnect` 的 `if (_connecting) return;` **静默返回（零日志）** |
| **铁证** | 22:45:00→22:50:56 共 **356 秒**（SPTick 约 23 次 tryConnect）`连接请求` **0 条**；心跳 `外设状态=0`（Disconnected）且心跳能打出（`_armed=YES`）⇒ 三层互锁，只可能死在守卫 |
| **竞态** | 同晚 23:22:58 第二次关蓝牙**自愈了**（关蓝牙发生在 retryLater 的 1 秒窗内，守卫没被置位）—— 同一动作，一次恢复、一次砖掉 |

**验收**：关蓝牙 → 再开 → 日志必须**立刻**出现 `连接请求 -> SDH-xxxxxx` + `蓝牙不可用(4) —— 作废本轮连接请求与握手`。

### v1.2.1 修复「按一次不开、要按两次」（2026-10-10 · 3 小时 09 分 · 42 次发起）

> 上一轮（1.2.0）审计用「订阅 / 就绪 / 帧1 / 完成 计数自洽」做判据。本轮换判据后当场破案。

| 指标 | 1.2.0 段（18:11→21:20） |
|:--|:--|
| 解锁发起 / 完成 | 42 / **35（83%）** |
| 「写特征就绪」/「解锁帧 1/4」 | **43 / 42 ← 差 1，账不平** |
| 链路断开 | 58 次 |
| 异常 / 崩溃 | **0** |

**破绽**：`_lastAt`（20 秒冷却锚点）**跨链路存活**。
`didDisconnectPeripheral` 清了 `_step / _wr / _nt / _doneLink / _linkAt / _connecting / _stallRetries`，
却漏了 `_lastAt`。于是「发到一半链路被断 → 立刻重连 → 新链路就绪」时，`directBegin`
被**上一条链路**的冷却静默 `return`（零日志），只能等 15.1 秒一跳的 `SPTick` 补发。

| 就绪时刻 | 帧 1 实际发出 | 延迟 |
|:--|:--|:--|
| **20:37:31** | **20:37:59** | **+28 s** ← 用户「按了两次」的那一回 |
| 21:09:23 | 21:09:34 | +11 s（恰为定时器第 701 拍） |
| 20:26:43 | （本轮从未发出） | — |

**修复**：`didDisconnectPeripheral` 补 `_lastAt = 0;`（断开即新一轮）；冷却分支补日志；
「就绪 → 立刻直发」文案改为「就绪 —— 请求直发」（原文案是提前宣称，与实际执行脱钩）。

**副作用核算**：本段相邻发起最小间隔 **27 秒**、`< 20 秒` 的次数 **0**
⇒ 发起总次数不变，不会出现「一次按键发两轮」。协议路径 **sha256 逐字节零改动**。

## 安全设计

SpringBoard 崩 = 注销，开机崩 = 白苹果循环，因此：

1. **kill-switch 是第一件事** —— 文件存在就直接 return，绝不碰蓝牙
2. 全部逻辑在后台队列，**不阻塞 SpringBoard 启动路径**
3. 逐层 `@try/@catch`，异常绝不外泄
4. **不做任何 swizzle**（纯新增行为）
5. 非 busy-loop —— 15 秒 tick + 退避 1→30 秒（**连上即复位**）+ 解锁冷却 20 秒 + 同链路只发一轮

- **与官方 App 会抢链路** —— 建议用前把官方 App 从后台划掉。
  1.2.0 起同秒双发连接请求已消除，但**两个 central 争同一辆车**这一点本质未变。
- 日志中偶见 `Failed to encrypt the connection` —— 在官方 App 版日志里也出现过，归因**蓝牙弱信号**；
  另一常见诱因是**同时有另一个 central 连着车**。二者无法从日志区分。
- 「车 UUID 未知」时（App 从未连过车）会进入扫描模式，认车最多多等 60 秒。
- **车回帧仅按长度匹配**（26 / 42）—— 这是继承自已量产官方 App 的宽松匹配，
  收紧只会降低解锁成功率，故保持原样。详见 CHANGELOG「明确不改」。

## 安全阀（kill-switch）

创建以下文件后注销桌面（respring）即停用，删除后重新注销即恢复：

```
/var/mobile/Library/Preferences/com.jibamao.spsundiro.off
```

1.2.0 起会同时探测**真实根 / `/var/jb`（rootless）/ 全部 `.jbroot-*`（RootHide）**，
所以无论你用哪种工具创建，都能被认到；命中时日志会留一行
`★ kill-switch 命中（<路径>）—— 不启动蓝牙`，可直接验证。
